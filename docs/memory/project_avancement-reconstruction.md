**Note d'outillage — republier un Artifact volumineux (avec images base64) après une session précédente** : l'action `Artifact action:"read"` sauvegarde le HTML complet dans un fichier local temporaire ; éditer CE fichier avec `Edit` (pas besoin de le régénérer de zéro) puis `publish` dessus. Si `publish` est refusé avec "n'a pas été vu en entier", c'est que l'outil exige d'avoir *réellement* relu (via `Read`, ligne par ligne si nécessaire) l'intégralité du fichier sauvegardé — y compris la ligne 1 (souvent un unique très long minified JS de runtime) — avant d'accepter la publication, même si ce fichier a déjà été lu une fois plus tôt dans la session. Une seule ligne contenant des images en `data:` base64 peut à elle seule dépasser le budget de tokens d'un appel `Read` (~25k) : il faut alors relire par petits `limit` (1-2 lignes) autour des lignes lourdes. Si `publish` est refusé une 2ᵉ fois en disant que le contenu envoyé est "identique à une version déjà refusée", refaire un `Artifact action:"read"` pour re-confirmer la version live avant de republier. **Précision du 2026-09-02** : pour éditer une ligne contenant un `data:` base64 (ex. ajouter une ligne juste après une icône existante), ne JAMAIS retyper le blob base64 dans `old_string` (risque élevé de transcription imparfaite sur une si longue chaîne → l'Edit échoue avec "String to replace not found") — ancrer l'edit sur un fragment COURT et unique en fin de ligne (ex. `alt="energie" title="energie.png"></span></td><td>Ressource d'équipe...</td></tr>`) plutôt que sur le src de l'image. Pour localiser les sections d'un fichier HTML volumineux sans en lire le contenu image, `Grep` avec `-o`/`-n` sur des motifs courts (ex. `<h2>.*</h2>|id="[a-z]+"`) donne une table des matières par numéro de ligne, bien moins coûteux que de lire tout le fichier à l'aveugle.
